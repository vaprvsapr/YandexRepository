# Event Manager API

RESTful API для управления событиями, написанное на C# с использованием ASP.NET Core (.NET 10)
и принципов чистой архитектуры (Dependency Injection, DTO, Repository Pattern).

## Требования

- **.NET 10 SDK** 
- Среда разработки (Visual Studio 2026 / Rider / VS Code)
- База данных PostgreSQL (локально или в облаке) для хранения данных событий и бронирований
- Docker (для запуска тестов с Testcontainers)

## Запуск проекта

В терминале выполните команду "docker compose up -d", чтобы поднять контейнер с PostgreSQL, Kafka и микросервисами.
При запуске проекта схема БД создается автоматически с помощью Migrate().

## Проверка работы через Swagger UI

Swagger UI микросервиса BookingMicroService доступен по адресу: `https://localhost:5001/swagger`.
Swagger UI микросервиса EventMicroService доступен по адресу: `https://localhost:5002/swagger`.
Swagger UI микросервиса UserMicroService доступен по адресу: `https://localhost:5003/swagger`.

### Через Visual Studio

1. Откройте решение в Visual Studio.
2. Убедитесь, что `EventMicroService.Presentation, BookingMicroService.Presentation, UserMicroService.Presentation` запускаются одновременно (несколько запускаемых проектов).
3. Нажмите `F5` или кнопку "Пуск" (IIS Express / http / https).
4. Автоматически откроется браузер со страницей **Swagger UI** для всех микросервисов, где можно протестировать API.

### EventMicroService

#### Архитектура

Сервис разделен на несколько проектов: EventMicroService.Presentation, EventMicroService.Application, EventMicroService.Infrastructure, EventMicroService.Domain
согласно принципам чистой архитектуры. Он предоставляет REST API для управления событиями, включая создание, обновление,
удаление и получение событий с поддержкой фильтрации и пагинации.

В микросервисе реализован фоновый обработчик бронирований `BookingProcessRequestBackgroundService`, который читает сообщения из топика `booking-process-request` о новых и отмененных бронированиях из 
Kafka и обрабатывает их, помещая сообщение в топик `booking-process-response`.

События хранятся в таблице `Events`, базы данных `eventapi-events-db`.

Реализован кэш событий с использованием Redis. Кэширование применяется для ускорения получения списка событий и о��дельных событий по их идентификатору.
Кэш события инвалидируется при удалении, обновлении события, а также при оформлении или отмене бронирования события.

Для отслеживания активных бронирований для конкретного события используется дополнительная таблица `EventBookings`,
которая хранит активные бронирования для каждого события. Эта таблица также принадлежит базе данных `eventapi-events-db`.
Этот функционал реализован для избежания повторного бронирования или повторной отмены одной брони.

#### Модель данных Event (событие)

| Свойство       | Тип                | Описание                                                                 |
|----------------|-----------------------------------------------------------------------------------------------|
| Id             | guid               | Идентификатор события (обязательное поле)                                |
| Title          | string             | Название события (обязательное поле)                                     |
| Description    | string             | Описание события (по умолчанию пустая строка)                            |
| StartAt        | datetime?          | Время начала события (обязательное поле, ISO 8601)                       |
| EndAt          | datetime?          | Время окончания события (обязательное поле, ISO 8601)                    |
| TotalSeats     | int                | Общее количество мест (обязательное поле, задаётся при создании)         |
| AvailableSeats | int                | Количество свободных мест (автоматически инициализируется как totalSeats)|
| Bookings		 | List<EventBooking> | Список бронирований, связанных с этим событием                           |

*Дата окончания (`endAt`) должна быть строго больше даты начала (`startAt`).*

#### Эндпоинты

| Метод    | Маршрут                      | Описание                                                  | Успешный ответ   | Возможные ошибки                   | Требуемая роль |
|----------|------------------------------|-----------------------------------------------------------|------------------|------------------------------------|----------------|
| `GET`    | `/events`                    | Получить коллекцию событий (поддерживает query-параметры) | `200 OK`         | `400 Bad Request`                  | Anonymous      |
| `GET`    | `/events/top`                | Получить топ 10 самых бронируемых событий                 | `200 OK`         |                                    | Anonymous      |
| `GET`    | `/events/{id}`               | Получить событие по его уникальному `id`                  | `200 OK`         | `404 Not Found`                    | Anonymous      |
| `POST`   | `/events`                    | Создать новое событие                                     | `201 Created`    | `400 Bad Request`, `409 Conflict`  | Admin          |
| `PUT`    | `/events/{id}`               | Обновить существующее событие по его `id`                 | `200 OK`         | `400 Bad Request`, `404 Not Found` | Admin          |
| `DELETE` | `/events/{id}`               | Удалить событие по его `id`                               | `204 No Content` | `404 Not Found`                    | Admin          |

#### EventRepository
EventRepository - реализация интерфейса IEventRepository для управления данными событий в базе данных.

#### CacheRepository
CacheRepository - реализация интерфейса ICacheRepository для управления кэшем событий в Redis.
Позволяет добавить, получить и удалить событие из кэша.
ПОзволяет добавить и получить топ событий.

#### EventService
EventService — сервис, реализующий бизнес-логику для управления событиями. 
- Поддерживает создание, удаление, обновление, получение одного события и получение списка событий с фильтрацией и пагинацией. 
- При создании события проверяет уникальность идентификатора, при обновлении и удалении — существование события. 
- Для получения списка событий поддерживает фильтрацию по названию, диапазону дат, а также постраничный вывод (пагинацию).
- Использует IEventRepository для взаимодействия с базой данных и обеспечивает корректную обработку данных событий.
- Использует ICacheRepository для кэширования событий в Redis, что ускоряет доступ к данным и снижает нагрузку на базу данных.
Инвалидация событий происходит при удалении, обновлении события, а также при оформлении или отмене бронирования события.
Инвалидация топа событий происходит по TTL.

#### BookingProcessRequestBackgroundService
BookingProcessRequestBackgroundService — это фоновый сервис, который обрабатывает запросы на бронирование событий.

#### Фильтрация и пагинация

Метод **GET `/events`** поддерживает гибкую систему фильтрации и разбиения на страницы через query-параметры.

##### Параметры фильтрации

| Параметр | Тип               | Обязательный | Описание                                                                       |
|----------|-------------------|--------------|--------------------------------------------------------------------------------|
| `title`  | строка            | Нет          | Подстрока. Возвращаются события, название которых содержит эту подстроку.      |
| `from`   | ISO 8601 datetime | Нет          | Начало временного диапазона. Возвращаются события, у которых `startAt >= from` |
| `to`     | ISO 8601 datetime | Нет          | Конец временного диапазона. Возвращаются события, у которых `endAt <= to`      |

##### Параметры пагинации

| Параметр   | Тип | Обязательный | Значение по умолчанию | Ограничения | Описание                                                |
|------------|-----|--------------|-----------------------|-------------|---------------------------------------------------------|
| `page`     | int | Нет          | 1                     | Минимум: 1  | Номер страницы для отображения. Первая страница — это 1 |
| `pageSize` | int | Нет          | 10                    | От 1 до 100 | Количество элементов на одной странице                  |

##### Примеры комбинаций параметров

```bash
# Базовый запрос (первая страница, 10 элементов)
GET /events

# Фильтрация по названию
GET /events?title=встреча

# Временной диапазон
GET /events?from=2026-05-01T00:00:00Z&to=2026-05-31T23:59:59Z

# Название + временной диапазон
GET /events?title=встреча&from=2026-05-01T00:00:00Z&to=2026-05-31T23:59:59Z

# Только пагинация
GET /events?page=3&pageSize=20

# Все параметры вместе
GET /events?title=встреча&from=2026-05-01T00:00:00Z&to=2026-05-31T23:59:59Z&page=2&pageSize=5
```

##### Как работает пагинация

Результат пагинирует события в порядке их получения из хранилища:
- Если всего **42 события** и `pageSize=10`:
  - Page 1 вернёт события 1–10
  - Page 2 вернёт события 11–20
  - Page 3 вернёт события 21–30
  - Page 4 вернёт события 31–40
  - Page 5 вернёт события 41–42

Поле `totalCount` в ответе всегда показывает **общее количество событий, удовлетворяющих условиям фильтрации** (независимо от пагинации).
Это позволяет клиенту вычислить общее количество страниц: `Math.Ceil(totalCount / pageSize)`.

### BookingMicroService

#### Архитектура

Сервис разделен на несколько проектов: BookingMicroService.Presentation, BookingMicroService.Application, BookingMicroService.Infrastructure, BookingMicroService.Domain
согласно принципам чистой архитектуры. Он предоставляет REST API для управления бронированиями событий, включая создание, получение и отмену бронирований.

При оформлении бронирования сервис помещает сообщение типа `BookingProcessRequest` в топик `booking-process-request` в Kafka, который затем обрабатывается фоновым сервисом EventMicroService.

Фоновый сервис `BookingProcessResponseBackgroundService` обрабатывает ответы микросервиса событий из топика `booking-process-response`, обновляя статус бронирования в базе данных.

| Метод    | Маршрут                      | Описание                                                  | Успешный ответ   | Возможные ошибки                   | Требуемая роль |
|----------|------------------------------|-----------------------------------------------------------|------------------|------------------------------------|----------------|
| `POST`   | `/events/{id}/book`          | Создать бронирование для события с указанным `id`         | `202 Accepted`   | `404 Not Found`, `409 Conflict`    | User / Admin   |
| `GET`    | `/bookings/{id}`             | Получить бронирование по его уникальному `id`             | `200 OK`         | `404 Not Found`                    | User / Admin   |
| `GET`    | `/bookings`                  | Получить список всех бронирований                         | `200 OK`         |                                    | Admin          |
| `DELETE` | `/bookings/{id}`             | Отменить бронирование по его уникальному  `id`            | `204 No Content` | `404 Not Found`, `403 Forbidden`   | User / Admin   |


#### Модель данных Booking (бронирование)

| Свойство     | Тип       | Описание                                                                      |
|--------------|-----------|-------------------------------------------------------------------------------|
| id           | guid      | Идентификатор бронирования (устанавливается при создании)                     |
| eventId      | guid      | Идентификатор события, к которому относится бронирование                      |
| userId       | guid      | Идентификатор пользователя, который забронировал событие                      |
| event		   | Event     | Ссылка на событие, к которому относится бронирование (навигационное свойство) |
| status       | string    | Статус бронирования: Pending, Confirmed, Rejected                             |
| createdAt    | datetime  | Дата и время создания бронирования (устанавливается при создании)             |
| processedAt  | datetime? | Дата и время обработки (подтверждения или отклонения)                         |

#### BookingRepository
BookingRepository — реализация интерфейса IBookingRepository для управления данными бронирований в базе данных.

#### BookingService
BookingService — сервис, реализующий бизнес-логику для работы с бронированиями событий. 
- Позволяет создавать новые бронирования для событий, получать отдельные бронирования по идентификатору, 
а также получать список всех бронирований для конкретного события. 
- При создании бронирования сервис отправляет запрос в микросервис событий для проверки существования события и доступности мест, 
- генерирует уникальный идентификатор брони, устанавливает статус <code>Pending</code> и сохраняет дату создания и обработки. 
- Все методы выбрасывают исключения ошибках (например, если событие или бронирование не найдено).
- Использует IBookingRepository для взаимодействия с базой данных и обеспечивает корректную обработку данных бронирований.

#### BookingProcessRequestBackgroundService
BookingProcessRequestBackgroundService — это фоновый сервис, который обрабатывает ответы на запросы бронирования событий.

## Формат ответов и Глобальная обработка исключений

Успешные ответы API возвращают сами данные, например, массив событий или конкретный объект `EventDto`, без дополнительной обертки.

### Пример ответа 200 OK (GET /events/1)
```json
{
  "id": 1,
  "title": "Еженедельное планирование",
  "description": "Обсуждение ключевых задач на следующую неделю",
  "startAt": "2026-05-15T10:00:00Z",
  "endAt": "2026-05-15T11:00:00Z"
}
```

Все возникающие в API ошибки обрабатываются с помощью **Global Exception Handling Middleware**. Это гарантирует, что клиенты всегда будут получать информацию об ошибках (`400 Bad Request`, `404 Not Found`, `409 Conflict`, `500 Internal Server Error`) в унифицированном и предсказуемом формате по стандарту **RFC 7807 (Problem Details)**.

### Пример ответа с ошибкой валидации (400 Bad Request)
```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "instance": "/events",
  "errors": {
    "startAt": [
      "Время начала события должно быть меньше времени окончания события."
    ]
  },
  "traceId": "00-cbdfdd3839afff381fc3d46068b1c7ae-f173bc6c6fbb4c73-00"
}
```
Свойство `instance` указывает на маршрут, при обращении к которому возникла ошибка.

## Миграции
Схема базы данных создается автоматически при запуске каждого микросервиса с помощью метода 'context.Database.Migrate()'. 
Это гарантирует, что все необходимые таблицы и связи будут созданы в базе данных без необходимости ручного применения миграций.

Для ручного применения миграций можно использовать следующие команды в терминале:
- Создание новой миграции: `dotnet ef migrations add MigrationName --project NameMicroService.Infrastructure --startup-project NameMicroService.Presentation`
- Применение миграций к базе данных: `dotnet ef database update`
- Откат миграции: `dotnet ef database update PreviousMigrationName`

## Тестирование
Тестирование реализовано только для микросервиса EventMicroService.
Тестовый проект EventMicroService.Tests.Unit тестирует работу EventService.
Проверяются все основные сценарии: создание, обновление, удаление, получение одного события и получение списка событий с фильтрацией и пагинацией.
Проверяется инвалидация кэша при мутирующих операциях.
